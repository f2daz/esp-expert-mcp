# ESP8266 – Besonderheiten

Der ESP8266 unterscheidet sich grundlegend von der ESP32-Familie. ESP32-Wissen (FreeRTOS-Tasks, zwei Kerne, viel RAM, ADC-Kalibrierung) nicht übertragen. Chipdaten mit `chip_info`, Pins mit `pin_check`.

## Architektur und Ausführungsmodell

- **Ein Kern**, Tensilica **LX106**, 80/160 MHz. Kein Bluetooth. Externer SPI-Flash (außer ESP8285).
- **Arduino-Core: kein FreeRTOS.** Der Sketch läuft kooperativ zusammen mit dem Wi-Fi-/TCP-Stack des SDK. Wer nicht zurückgibt, blockiert das Netzwerk.
- Zurückgeben an das System: Ende von `loop()`, `delay(ms)`, `yield()` (= `delay(0)`).
- **Software-Watchdog** (Meldung `Soft WDT reset`, mit Stacktrace) und Hardware-Watchdog (Reset ohne Stacktrace) greifen bei zu langer Blockade.
- Richtwerte aus der Core-Doku: `loop()`-Durchläufe ohne `delay()` über ca. 50 ms gefährden die Wi-Fi-Stabilität; `delayMicroseconds()` gibt nicht ab – nicht über ca. 20 ms.
- **Stack nur ca. 4 KB** (Arduino-Core) – keine großen lokalen Puffer/Objekte.

```cpp
// Falsch: blockiert, Soft-WDT
while (!sensorReady()) {}

// Richtig: zeitbegrenzt und mit yield()
const uint32_t t0 = millis();
while (!sensorReady()) {
  if (millis() - t0 > 500) { handleTimeout(); break; }
  yield();
}
```

- Nicht-blockierend programmieren: Zustandsautomaten mit `millis()`, `Ticker` für periodische Aufgaben (Callback kurz halten, nur Flag setzen).
- **Callbacks** von Wi-Fi-Events, `Ticker`, Async-Bibliotheken (ESPAsyncTCP/-WebServer) laufen im SYS-Kontext: dort kein `delay()`, `yield()`, keine langen Operationen, keine blockierenden Netzwerkaufrufe. Flag setzen, Arbeit in `loop()` erledigen.

## ISR

- ISR mit **`IRAM_ATTR`** markieren (sonst Crash bei `attachInterrupt`, weil Flash-Cache gerade belegt sein kann). `ICACHE_RAM_ATTR` ist die ältere Schreibweise (in neuen Cores veraltet, prüfen) – in neuem Code `IRAM_ATTR`.
- In der ISR verboten: `delay()`, `yield()`, `malloc`/`free`/`new`/`delete`, `String`, `std::vector`, `Serial.print`.
- ISR kurz halten (Laufzeiten > 1 ms stören Wi-Fi/TCP). Geteilte Variablen `volatile`, Mehrbyte-Zugriffe in `loop()` mit `noInterrupts()`/`interrupts()` kurz schützen.
- **GPIO16 kann keine Interrupts.**

```cpp
volatile uint32_t pulses = 0;
void IRAM_ATTR onPulse() { pulses++; }

void setup() {
  pinMode(D5, INPUT_PULLUP);                    // D5 = GPIO14
  attachInterrupt(digitalPinToInterrupt(D5), onPulse, FALLING);
}
```

## Speicher: Heap, Fragmentierung, Flash-Strings

- Heap ist klein (typisch einige zehn KB frei nach Wi-Fi-Start; mit `ESP.getFreeHeap()` messen, nicht schätzen). **Out-of-Memory ist laut Core-Doku die häufigste Crash-Ursache.**
- Diagnose: `ESP.getFreeHeap()`, `ESP.getMaxFreeBlockSize()` (größter zusammenhängender Block), `ESP.getHeapFragmentation()` (0 % sauber, > ~50 % kritisch).
- Fragmentierung vermeiden:
  - Kein wiederholtes `String`-Verketten in `loop()`; wenn `String`, dann `reserve()`; besser feste `char`-Puffer + `snprintf`.
  - Puffer einmal allokieren und wiederverwenden; keine `new`/`delete` im Takt.
  - TLS (BearSSL) braucht viel RAM – Puffergrößen (`setBufferSizes`) reduzieren, wenn Server MFLN unterstützt.
- Konstante Strings in den Flash:
  ```cpp
  Serial.println(F("Start"));                      // String-Literal im Flash
  static const char HTML[] PROGMEM = "<html>...</html>";
  server.send_P(200, "text/html", HTML);           // _P-Varianten lesen aus PROGMEM
  char c = pgm_read_byte(HTML + i);                // manueller Zugriff
  ```
  `pgm_read_byte/word/dword/float/ptr` für PROGMEM-Daten; Flash-Daten nur ausgerichtet (4 Byte) lesbar – direkte Byte-Zugriffe auf PROGMEM ohne `pgm_read_*` können Exception 3 auslösen.
- Speicheraufteilung Cache/IRAM über Board-Option `mmu` (z. B. `3232` balanced, `4816` mehr IRAM).

## Pins und Boot

| GPIO | Besonderheit |
|---|---|
| 0 | Strapping: LOW beim Boot = UART-Download. Extern Pull-up; Taster nach GND ok |
| 2 | Strapping: muss beim Boot HIGH sein; oft Onboard-LED |
| 15 | Strapping: muss beim Boot LOW sein (Pull-down auf Modulen) |
| 1, 3 | UART0 TX/RX (Serial, Flashen) |
| 6–11 | **Flash-SPI – nicht verwenden** (Crash). ESP8285: GPIO9/10 je nach Modul nutzbar |
| 16 | Kein Interrupt, kein PWM/I2C üblich; `INPUT_PULLDOWN_16`; für Deep-Sleep-Wake mit RST verbinden |
| A0 | Einziger ADC, 10 Bit, **0–1,0 V am Chip** (Boards mit Teiler: D1 mini/NodeMCU ca. 0–3,2/3,3 V – Board prüfen) |

Bootmodi: **Flash-Boot** GPIO15=0, GPIO0=1, GPIO2=1; **UART-Download** GPIO15=0, GPIO0=0, GPIO2=1.

- Externe Beschaltung an GPIO0/2/15 so wählen, dass die Boot-Pegel nicht verletzt werden (z. B. keine Last, die GPIO2 beim Reset auf LOW zieht).
- ADC: `analogRead(A0)` liefert 0–1023. Mit `ADC_MODE(ADC_VCC);` (global) misst A0 stattdessen die Versorgung (`ESP.getVcc()`), A0 dann unbeschaltet lassen. Während Wi-Fi aktiv ist, wird `analogRead()` gedrosselt.
- PWM (`analogWrite`) ist Software-PWM: Standardbereich 0–255 ab Core 3.0 (davor 0–1023), Standard 1 kHz, `analogWriteFreq()`/`analogWriteRange()`.
- Pegel 3,3 V, nicht 5-V-tolerant (keine Freigabe im Datenblatt – nicht darauf verlassen).

## Deep Sleep

```cpp
ESP.deepSleep(60e6);           // µs; Wake nur, wenn GPIO16 mit RST verbunden ist
// max. Dauer: ESP.deepSleepMax()
```
- Nach dem Wake startet der Chip neu (`setup()` von vorn); Zustand in RTC-Speicher (`ESP.rtcUserMemoryWrite/Read`) oder Flash.
- Modi: `WAKE_RF_DEFAULT`, `WAKE_RFCAL`, `WAKE_NO_RFCAL`, `WAKE_RF_DISABLED`.
- Verbindung GPIO16–RST kann das Flashen per Auto-Reset stören → ggf. per Jumper/Widerstand lösbar machen (prüfen je Board).
- Reset-Grund: `ESP.getResetReason()`.

## ESP8285

- ESP8266 mit **1 MB integriertem Flash** (DOUT); dadurch sind GPIO9/10 je nach Modul frei.
- 1 MB reicht für OTA nur mit kleinem Sketch und kleinem/keinem Dateisystem.

## Flash-Layout und Dateisystem

```
| Sketch | OTA-Bereich | Dateisystem | EEPROM | Wi-Fi-Config (SDK) |
```
- Layout wird über die Board-Option `eesz` gewählt (z. B. `4M2M` = 4 MB, 2 MB FS; `4M` = ohne FS). PlatformIO: `board_build.ldscript = eagle.flash.4m2m.ld`.
- **LittleFS statt SPIFFS**: SPIFFS ist im Core deprecated und kann entfallen. `#include <LittleFS.h>`, `LittleFS.begin()`. Unterschiedliche Formate – Umstieg heißt Neuformatieren.
- Neues Sketch-Flashen verändert das Dateisystem nicht; `erase`/„Erase Flash: All Flash Contents“ schon.
- Konfigurierte Flash-Größe darf nicht kleiner/größer als die reale sein (Symptom: FS-Mount-Fehler, OTA scheitert).

## OTA

- Der Flash muss **alte und neue Firmware gleichzeitig** aufnehmen: neue Firmware wird zwischen Sketch und Dateisystem abgelegt, dann kopiert eboot sie beim Neustart. Faustregel: **Sketch ≤ halber freier Bereich** (Sketch + OTA-Bereich).
- Vor dem Update prüfen: `ESP.getFreeSketchSpace()` ≥ Größe der neuen Firmware.
- ESP-01 mit 512 KB: praktisch kein OTA. Großes FS verkleinert den OTA-Platz.
- ArduinoOTA mit Passwort absichern; `ESP8266HTTPUpdate` für Pull-Updates (TLS-RAM-Bedarf beachten).

## Exceptions und Crash-Analyse

- Crash-Ausgabe zwischen `--------------- CUT HERE FOR EXCEPTION DECODER ---------------` kopieren, mit **der ELF des aktuell geflashten Sketches** dekodieren:
  `serial_log_analyze`, PlatformIO-Filter `esp8266_exception_decoder` oder EspExceptionDecoder (Arduino IDE).
- Exception-Codes (EXCCAUSE): `0` Illegal Instruction, `2`/`3` Adress-/Datenfehler bei Instruction Fetch bzw. Load/Store (z. B. Byte-Zugriff auf Flash/PROGMEM ohne `pgm_read_*`, ISR ohne `IRAM_ATTR`), `6` Division durch Null, `9` unausgerichteter Zugriff, `28`/`29` unerlaubter Lese-/Schreibzugriff (typisch Nullpointer oder freigegebener Speicher).
- `Soft WDT reset` → blockierender Code ohne `yield()`; `wdt reset` ohne Stack → Hardware-WDT (oft blockierte ISR oder abgeschalteter Soft-WDT).
- `rst cause`/`boot mode` in der ROM-Ausgabe (74880 Baud) zeigen Reset-Grund und Bootmodus – Monitor dafür auf 74880 stellen.

## ESP8266_RTOS_SDK

- Espressifs FreeRTOS-basiertes SDK im IDF-Stil. Laut Ankündigung im Repo (Issue #1166) **keine neuen Hauptversionen und keine neuen Features** mehr, Komponenten nur bei Bedarf aktualisiert (prüfen). Support-Policy: 18 Monate je Minor-Release, LTS 30 Monate; V3.2 und älter sind EOL, Status von V3.3+/V3.4 in der Policy bzw. Release-Branches prüfen.
- Für neue Projekte nicht empfehlenswert; Bestandsprojekte auf gewartetem Release-Branch halten.
- Arduino-Core und ESPHome setzen nicht darauf auf (Arduino-Core nutzt NONOS-SDK-Basis).

## Wann ESP8266 heute noch sinnvoll ist

- Bestandsgeräte (Sonoff, Shelly Gen1, D1-mini-Aufbauten), Wartung vorhandener Firmware, einfache ESPHome-/Tasmota-Sensoren.
- Sehr kostenkritische, einfache Wi-Fi-Sensoren ohne TLS-lastige Kommunikation.
- **Neuentwicklung:** besser ESP32-C3/C6 (RISC-V, FreeRTOS, BLE, mehr RAM, aktiv gepflegtes ESP-IDF, Secure Boot/Flash-Encryption) – Pin- und Bauform-Kompatibilität mit `chip_info`/`pin_check` prüfen.
